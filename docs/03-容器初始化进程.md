# 03 - 容器初始化进程

## 父进程与初始化进程

runtime 父进程留在宿主环境中，负责管理容器。初始化子进程进入容器 namespace，设置 rootfs 和进程属性，最后通过 `execve` 变为 OCI 配置指定的程序。

re-exec 表示父进程重新执行自己的可执行文件，得到一个从入口重新运行的子进程。子进程不会继承父进程内存中的 Go 配置对象，因此需要通过管道等通信方式接收初始化配置。

## 初始化通信

两条管道分别传递配置和结果：父进程发送解析后的 rootfs 绝对路径及 OCI 配置；子进程返回初始化成功或具体错误。通信管道与程序的 stdin、stdout、stderr 分开，避免日志或程序输出被当作控制消息。

每条管道只发送一份 JSON。发送方写完后关闭写端，接收方读取到 EOF 后解析整份消息。EOF 本身不代表成功，空消息和截断消息都必须报错。

配置管道也可以作为初始化屏障：父进程先把子进程加入 cgroup，再发送配置并关闭写端。子进程此前只等待配置，不能提前执行 rootfs、身份切换等初始化操作；加入失败时父进程终止并回收子进程。这种单次放行不需要额外管道。

初始化成功也不等于用户程序已经执行。后续启动仍可能因为权限、程序路径或动态链接器等原因失败，需要由执行阶段另行报告。

## 匿名管道与文件描述符

`os.Pipe()` 创建内核中的匿名管道，返回读端和写端。匿名管道没有文件路径；`mkfifo` 创建的有名管道才需要通过路径打开。`io.Reader` 和 `io.Writer` 只是 Go 的读写接口，可以由管道、普通文件或内存对象实现。

父进程通过 `exec.Cmd.ExtraFiles` 把配置读端和结果写端交给子进程。数组第一个文件在子进程中是 fd 3，第二个是 fd 4；fd 0、1、2 分别是 stdin、stdout、stderr。子进程用 `os.NewFile` 包装已有 fd，它不会再次创建管道。

父进程还传递自身的 mount、UTS namespace 句柄，分别映射为 fd 5、fd 6。这些句柄用于比对 namespace 对象，并非通信管道。子进程检查句柄类型，再通过设备号与 inode 确认自身位于不同的 namespace；修改挂载前必须核对 mount 隔离，设置 hostname 前必须核对 UTS 隔离。比对后关闭这些句柄。

子进程启动后，父进程必须关闭自己不使用的端点。只有管道的所有写端引用都关闭，且已有数据读完，读端才会得到 EOF。即使子进程已经退出，父进程遗留的写端也会让读取一直等待。

配置已接收、隔离环境已准备好、用户程序已启动是不同阶段。父进程应根据实际完成的阶段解释确认消息，不能仅凭收到消息就把容器标为 running。通信失败时，应终止未完成初始化的子进程，再通过 `Wait` 回收。

## exec 与进程回收

`execve` 替换当前进程执行的程序，PID 和父子关系保持不变。初始化进程变为 bash 等用户程序后，父进程仍然可以等待同一个子进程退出。

`Wait` 等待子进程退出并取得退出状态。进程退出后，内核暂时保留退出状态等记录；收取这些信息后才完成回收。尚未被回收的退出进程称为僵尸进程，发送终止信号不能代替回收。

前台 `run` 留下父进程，等待容器程序退出并处理信号。`create/start` 完成对应操作后返回，后续命令通过状态目录找到容器；原父进程退出后，内核将子进程交给收养者，由其负责回收。在 containerd 集成中，这一职责由长期运行的 shim 承担。runtime 无需常驻守护进程，但仍需保存必要的容器状态。

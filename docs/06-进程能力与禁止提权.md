# 进程能力与禁止提权

## capabilities

Linux 把部分特权拆成独立能力。例如 `CAP_SYS_ADMIN` 涉及挂载等管理操作，`CAP_SETUID` 允许改变用户身份。UID 是 0 不等于必须给程序全部能力，切换到普通用户也不等于不能保留指定能力。

OCI 的 `process.capabilities` 包含五个集合：

| 集合 | 作用 |
| --- | --- |
| permitted | 当前可以设置到 effective 的能力范围 |
| effective | 内核检查特权操作时实际使用的能力 |
| inheritable | 与可执行文件的 inheritable 能力共同参与 exec 后的能力计算，并非自动完整继承 |
| bounding | 限制 exec 时从文件 permitted 获得的能力，只能缩小，不能补回 |
| ambient | 满足条件时跨普通程序 exec 保留，并进入新的 permitted/effective |

effective 必须是 permitted 的子集，ambient 必须同时属于 permitted 和 inheritable。permitted/inheritable 不必是 bounding 的子集。配置无法让初始化进程凭空获得宿主没有的 permitted，也无法恢复已经丢弃的 bounding。

minirunc 用明确的能力名称解析配置，拒绝未知名称、重复项和非法集合关系。省略 capabilities 的策略是清空全部集合，不继承启动者的特权；这是本运行时的默认策略，不是所有 OCI 实现都采用的默认值。

## 身份切换顺序

从 root 切换到非 root 时，内核通常清除 permitted 和 effective。若配置要求非 root 保留能力，初始化线程临时启用 `PR_SET_KEEPCAPS`，只让 permitted 跨过身份切换；effective 仍需重新设置。

初始化先完成挂载和资源限制，再清除继承的 ambient、准备 inheritable、缩小 bounding，按需临时保留 permitted，设置附加组、GID、UID，关闭临时 KEEP_CAPS，设置最终 permitted/effective/inheritable，最后设置 ambient。提前准备 inheritable 是因为 bounding 缩小后可能不再允许新增相应的 inheritable 位。

`capget/capset` 的 v3 ABI 使用两组 32 位数据表示 64 位能力集合。运行时还需查询内核实际支持的编号，不能只按自己认识的名称清理，以免新内核上的其他能力遗留。

## no_new_privs

`process.noNewPrivileges: true` 通过 `prctl(PR_SET_NO_NEW_PRIVS, 1)` 启用，阻止后续 exec 利用 setuid/setgid 位或文件 capabilities 获得额外权限。它不会撤销已有权限，也不代替 capabilities、user namespace 或 seccomp。

标志一旦启用就不能关闭，子进程继承，exec 后也保留。配置为 false 时不尝试清除继承的标志。初始化在最终能力设置后启用它，然后以最终权限进入工作目录。

## Go 初始化线程

能力集合、bounding、ambient 和 no_new_privs 都是线程属性。初始化 goroutine 必须固定在 OS 线程上，随后在同一线程完成初始化和 exec，不能解锁后回到普通业务逻辑。

Go 的 UID/GID 封装会同步进程内各线程，但这不意味着 capset/prctl 也会自动同步。其他 Go 线程不执行容器用户代码，最终 exec 会销毁它们；在 exec 之前不能把初始化进程当作已经能运行任意用户代码的安全边界。任何一步失败都必须终止初始化，由父进程回收并清理 cgroup。

本阶段验证的是初始化线程的能力和标志。用户程序 exec 后的能力仍受内核的身份、文件能力与 ambient 规则影响，不能把 exec 前的 effective 简单视为执行后的保证。
